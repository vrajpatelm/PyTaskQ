## PyTaskQ 0.7.0

```bash
pip install -U pytaskq
```

Docker: `ghcr.io/vrajpatelm/pytaskq:0.7.0` (also `0.7` and `latest`), for amd64 and arm64.

**Upgrade if you run 0.6.x.** Four break tests of 0.6 found ways for one bad job or one Redis hiccup to hurt the whole fleet. 0.7.0 fixes all of them, and a 20-minute chaos test (killed workers, Redis restarts, refused writes, frozen processes, all under load) checked the result. Read [Upgrading from 0.6.1](https://github.com/vrajpatelm/PyTaskQ/blob/main/docs/UPGRADING.md#from-061-to-070) first: a few things are stricter.

### One bad job can't take the fleet down

- **A job that crashes its worker** (a segfault in a C extension, the out-of-memory killer, code holding Python's GIL) used to be handed to the next worker, which crashed too, forever. Now it's dead-lettered after `MAX_RECOVERIES` (3) with the reason.
- **An async task that ignores cancellation** can't hold a slot or stop its worker from exiting any more.
- **One backed-up queue** no longer freezes every other queue's scheduled jobs and retries.

### Redis trouble doesn't lose or repeat jobs

- Read-only replicas during a failover, too few replicas, a failed disk save, another client's long Lua script, a restart loading data: the finished job's outcome is kept and saved when Redis takes writes again. It isn't run twice.
- Another app's key under one of PyTaskQ's names can't lose a job; the log names the key.
- Eviction switched on while running, and data under another key prefix, are logged.

### Fairer, steadier, faster

- Every queue gets an equal share of every priority.
- `rate_limit` keeps its spacing even when jobs wait for a free thread.
- A worker takes up to 8 jobs per round trip: a Redis in another zone no longer caps it at one job per round trip.
- `delay_sync()` reuses its connections; `await delay()` works from any event loop.
- The leader hands over at once on a clean stop (no 20-second scheduling gap per deploy).

### New

- `Unrecoverable`: raise it to dead-letter a job at once, without retries.
- `with_job(fn)`: `progress()` and `cancelled()` from threads your task starts.
- Cron `overlap=False`: skip a tick while the previous run is still going.
- Rolling deploys: a job for a task no worker has yet waits for one (`UNKNOWN_TASK_WAIT`, 10 minutes).
- SIGHUP stops a worker cleanly; a second Ctrl+C skips the grace period.
