## PyTaskQ 0.5.0

```bash
pip install -U pytaskq
```

Docker: `ghcr.io/vrajpatelm/pytaskq:0.5.0` (also `0.5` and `latest`), for amd64 and arm64.

This is the first release on PyPI since **0.3.1**. Versions 0.4.0 to 0.4.2 were only tagged on GitHub, so everything below is new if you installed from PyPI. **Before upgrading, read [docs/UPGRADING.md](https://github.com/vrajpatelm/PyTaskQ/blob/main/docs/UPGRADING.md)**: a few defaults changed (cron runs in UTC, priorities are weighted, the API checks arguments), and Redis must be set to `maxmemory-policy noeviction`.

### Highlights

**Control running work**
- `pytaskq.progress(percent, message)` from any task, shown as a progress bar in the dashboard.
- Stop a **running** job from the dashboard, the API or `app.cancel()`. Async tasks are cancelled, CPU tasks' processes stopped, long IO tasks check `pytaskq.cancelled()`.
- `@app.task(max_concurrency=2)` and `@app.task(rate_limit="100/m")`, enforced across all workers.
- Pause and resume a queue with one click.

**Find anything**
- A **History** tab and `GET /tasks/history`: search every kept finished job by text, outcome, task, queue and time.
- `/metrics/prometheus` for Grafana and alerts.

**Fast and lean**
- Idle workers start a new job in **1–3 ms** (was up to a second) and barely touch Redis while idle.
- **Redis memory stays flat** at any volume: only the newest `FINISHED_JOBS_KEPT` (50,000) finished jobs are kept.
- On a 2-core server with 500 simultaneous users: typical response 16 ms (was 320 ms), and no more "Redis unavailable" errors (was 14% of requests).

**Built for production**
- **Named queues** (`@app.task(queue="images")`, `pytaskq worker --queues images`) so heavy work gets its own workers.
- **Fair priorities**: high jobs go first most of the time, default and low ones still move (`PRIORITY_WEIGHTS=6,3,1`).
- **Cron**: time zones per task (`tz="Asia/Kolkata"`), and runs missed during an outage are reported and the latest one runs once (`catch_up`).
- **High availability**: Redis Sentinel support (tested with a real failover: back within about 3 seconds, no confirmed job lost) and `REDIS_WAIT_REPLICAS` so a queued job is on two machines.
- **Share one Redis** between installations with `REDIS_KEY_PREFIX`.
- **Idempotency keys** (`Idempotency-Key` header, `delay(..., idempotency_key=…)`): retried submissions queue one job.
- **OpenTelemetry tracing** from the request that queued a job through every attempt.
- **Settings → Performance** explains in plain words what to change: queues filling up, Redis heading for full or set to lose data, workers on different versions or settings, missed schedules, blocked event loops, stuck threads.

**Hardened by two break tests**
Crashed and hung tasks, Redis outages mid-job, a full or wiped Redis, frozen event loops, floods of requests and invalid jobs were all tried on a real Redis with real worker processes. Among the fixes: a crashed CPU task no longer freezes its worker, a timed-out task no longer blocks the next ones, a job finishing during a Redis outage is saved once Redis is back, workers start (and free memory) while Redis is full, and graceful shutdown puts unfinished jobs back on their queue.

### Breaking changes at a glance (from 0.3.1)
- Cron schedules are read in **UTC** unless a task sets `tz=` (or `CRON_TIMEZONE`).
- Priorities are **weighted** (`PRIORITY_WEIGHTS=strict` for the old behaviour).
- The API answers `422` for arguments a task doesn't accept, `413` for jobs over 1 MB, `403` for internal task names, `422` for unknown queues.
- `QUEUE_CAPACITY` applies to each queue; `0` now means no limit.
- At most 50,000 finished jobs are kept (`FINISHED_JOBS_KEPT`).
- Cancelling a running job stops it (`202`) instead of `409`.
- `apply_async(task_id=…)` with the id of an active job raises `TaskIdInUse`.
