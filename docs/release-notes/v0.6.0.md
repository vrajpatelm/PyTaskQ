## PyTaskQ 0.6.0

```bash
pip install -U pytaskq
```

Docker: `ghcr.io/vrajpatelm/pytaskq:0.6.0` (also `0.6` and `latest`), for amd64 and arm64.

**Upgrade if you run 0.5.0.** With redis-py 8 (what `pip install` gives today), idle 0.5.0 workers picked up new jobs up to 4 seconds late and logged a false `TimeoutError` every 10 seconds. 0.6.0 fixes that and everything else two break tests found, and adds workflows. Read [Upgrading from 0.5.0](https://github.com/vrajpatelm/PyTaskQ/blob/main/docs/UPGRADING.md#from-050-to-060) first: a few things are stricter.

### New: workflows

```python
from pytaskq import chain, group

wf = await app.workflow(chain(
    download.s("https://example.com/photo.jpg"),
    group(resize.s(size=64), resize.s(size=512)),   # at the same time
    publish.s(channel="cdn"),                        # gets both results
), name="Photo thumbnails")
```

- Stages one after another, groups side by side, each step's result passed on.
- `on_failure="stop"` or `"continue"`. After a failure, fix the cause and **retry the failed steps: the workflow resumes** where it stopped.
- A **Workflows** tab shows every stage and step, why a workflow stopped, and Retry / Cancel buttons.
- Start one from any language with `POST /workflows` (with `Idempotency-Key` for safe retries).
- Steps run on their task's own queue and priority, a group's results are stored once (not copied into every next step), cancelling stops every remaining step, and the leader recovers a stage whose worker died at any point. All of this was checked with a break test of workflows together with retries, timeouts, cancelling, dead letters, limits, paused queues, key prefixes and killed workers.
- No result backend and no polling: the next stage starts exactly once, from one atomic step in Redis.

Guide: [docs/WORKFLOWS.md](https://github.com/vrajpatelm/PyTaskQ/blob/main/docs/WORKFLOWS.md)

### Fixed: what task code can do to a worker
- `sys.exit()` or `KeyboardInterrupt` in a task (argparse and click call `sys.exit`) **stopped the worker**, and then every worker the job went to next. Now that job fails with `TaskExited`.
- Text that isn't valid UTF-8 (file names from `os.listdir()`) in a result or error left the job **stuck in Processing**, running again on every restart.
- An `async def` behind an ordinary decorator **never ran** but showed as Succeeded.
- Huge error messages were stored and sent in full (60 MB list responses); they're cut to 4 KB.
- `NaN` results were stored as invalid JSON.

### Fixed: limits, cancelling, lost replies
- `max_concurrency` could be exceeded when IO jobs timed out, and managed only about one start per second, in random order. Now places follow the real thread and **waiting jobs start the moment a place frees up, oldest first** (20 × 0.1 s jobs: 2 s instead of 70).
- `rate_limit` let jobs through in bursts after a pause or a replay, and cancelled jobs kept their turns.
- A cancelled job could start again after a worker restart.
- A lost Redis reply could make a queued job look failed (`TaskIdInUse`), run a job twice, or create two dead letters.
- Two containers with the same worker name could run the same job twice.
- Replaying a dead letter while the same id ran started a second copy.

### Fixed: connections
- Idle workers on redis-py 8 timed out every cycle (pickup up to 4 s); on redis-py 5–7 a silently dropped connection could freeze a worker forever. Every connection now has an explicit timeout and TCP keepalive, and the worker checks its own connections.
- With Redis Sentinel, idle workers timed out every 7 s.

### Also
- The SDK checks arguments against the task's signature (`TypeError` at once); `delay()` and `delay_sync()` take `countdown=` and `task_id=`.
- `GET /dlq` is paged; job lists send compact records; history search reads small fields only.
- Cron runs for a paused queue are skipped instead of piling up.
- *Settings → Performance* warns when Redis has no memory limit.
